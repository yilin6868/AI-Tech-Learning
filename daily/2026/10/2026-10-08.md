# 2026-10-08 AI 技术深度日报｜mattpocock/skills：用反馈循环约束 AI 调试

> 今日研究原则：只研究一个项目和一个主要问题。今天不评价整套 Skills 的所有能力，只验证 `diagnosing-bugs` 是否会约束 Agent 先建立失败信号，再分析根因。

## 今日结论

- **今日项目**：[mattpocock/skills](https://github.com/mattpocock/skills)
- **所属方向**：AI Agent / AI 编码工作流
- **一句话理解**：它不是让 AI 单纯更快地写代码，而是把需求澄清、测试、调试和评审等工程方法写成可重复执行的 Skill，让开发过程更可控、稳定、可验证。
- **我的判断**：值得试用，但目前只验证了 `diagnosing-bugs` 的一次受控流程，不能把结果外推到整套项目或所有真实 Bug。
- **今天最重要的收获**：调试的第一步不是阅读源码和猜原因，而是建立一条能够精确捕获用户症状、稳定变红、修复后可以变绿的反馈循环。

## 大白话解释

可以把 `diagnosing-bugs` 理解成一张“AI 修 Bug 操作清单”。

普通 AI 看到 Bug，可能马上翻代码、猜原因、直接修改。运气好能修对，运气不好就会越改越乱。这个 Skill 要求 AI 按顺序做：

1. 先做一个“报警器”，Bug 存在时它就报错。
2. 确认这个报警器每次都能抓到同一个问题。
3. 列出几个可能的原因，再一个一个验证和排除。
4. 找到真正原因后再改代码，最后用同一个报警器确认 Bug 消失。

我们模拟的问题是：订单满 `50.00` 元应该免运费，程序却收了 `5.00` 元。我们先让检查程序连续三次抓到这个问题，然后排除了“比较符号写错”和“免运费门槛写错”，最后发现程序在计算前把金额减掉了 `0.01` 元，所以 `50.00` 元被当成了 `49.99` 元。

> 最简单的结论：这个 Skill 不一定让 AI 修 Bug 更快，但能让 AI 少靠猜、多靠证据，降低修错和乱改代码的风险。本次实验只找到了原因，还没有修改程序。

## 它是怎么工作的

```mermaid
flowchart LR
    A[输入：需求或故障症状] --> B[选择匹配的 Skill]
    B --> C[按阶段与检查点执行]
    C --> D[产生问题、测试、证据或代码]
    D --> E[用反馈信号验证结果]
```

### 核心组件

1. **用户调用型 Skill**：由用户主动触发，用于组织完整流程，例如需求追问、规格拆解或实现。
2. **模型调用型 Skill**：在任务匹配时由 Agent 使用，提供可复用的工程纪律，例如 TDD、Bug 诊断和代码评审。
3. **阶段门控与完成标准**：要求前一阶段取得明确证据后才能进入下一阶段，减少 Agent 跳步和过早下结论。

### 我对技术原理的理解

- 它与普通 Prompt 的区别：普通 Prompt 往往只描述目标；这些 Skills 还规定执行顺序、禁止事项、证据要求和退出条件。
- 最关键的技术设计：把“先建立反馈循环”设为诊断的强制门槛，没有能捕获真实症状的红色信号，就不能进入假设和修复阶段。
- 我还没有完全理解的部分：不同模型、不同代码库和复杂线上故障下，Agent 能否稳定遵守这些门控；多个 Skills 组合时是否会发生规则冲突。

## 试用设计

### 实验目标

- 我要验证：使用 `diagnosing-bugs` 时，Agent 是否会先建立可重复的失败检查，再提出假设和查看实现。
- 成功标准：在查看被随机选中的实现之前，先运行一条能精确捕获故障的命令；该命令连续运行结果一致；随后用多个可证伪假设和定向证据确认根因。
- 失败标准：Agent 先读实现并直接猜原因、没有运行失败检查，或检查只能证明程序没有崩溃而不能捕获用户的具体症状。
- 排除替代解释：从三种会产生相同表面症状的实现中随机选择一种，在红色反馈循环建立前不查看最终选中了哪一种。

### 试用环境

- 操作系统：macOS
- 使用端：Codex 桌面应用
- 项目版本：2026-10-08 从 `main` 分支安装的快照；安装器没有记录精确提交 SHA，因此版本号标为待确认。
- 关键配置：仅安装 `skills/engineering/diagnosing-bugs`，没有安装整套仓库；受控程序放在临时目录中，没有修改学习仓库代码。
- 是否涉及外部 API 或付费服务：下载 Skill 时访问 GitHub；实验本身使用 Python 标准库，不使用外部 API、密钥或付费服务。

### 操作步骤

1. 写下假设、成功标准和失败标准，经用户同意后安装 `diagnosing-bugs`。
2. 创建一个免运费计算 CLI，并从三种同症状故障中随机选择一个实现；已知症状是小计 `50.00` 应免运费，实际返回 `5.00`。
3. 在查看所选实现前运行 `python3 check_bug.py`，连续三次确认同一症状稳定变红。
4. 列出三个可证伪假设，依次用黑盒输入、内部阈值检查和最终源码检查排除错误假设。

## 实验结果

| 阶段 | 操作 | 实际现象 | 判断 |
| --- | --- | --- | --- |
| 建立反馈循环 | 连续三次运行 `python3 check_bug.py` | 三次均报告期望 `0.00`、实际 `5.00`，退出码均为 1 | 精确捕获原始症状，结果稳定 |
| 排除边界比较错误 | 运行 `python3 app.py 50.001` | 仍返回 `5.00` | 如果只是 `>` 与 `>=` 错误，此输入应免运费，因此该假设被排除 |
| 排除阈值常量错误 | 定向检查内部免运费阈值 | 阈值为 `50.00` | 排除阈值被写成 `50.01` 的假设 |
| 确认输入偏移 | 查看被选中的实现，并运行 `python3 app.py 50.01` | 源码在比较前减去 `0.01`；`50.01` 返回 `0.00` | 黑盒预测与源码一致，根因确认 |

### 最终验证结果

- 是否达到成功标准：是。Agent 在查看被选中的实现前先建立并运行了红色反馈循环，随后通过多个可证伪假设收敛到根因。
- 可复现的证据：`python3 check_bug.py` 在故障存在时稳定退出 1，并明确输出 `subtotal=50.00 expected shipping=0.00, actual=5.00`。
- 实际耗时：三次反馈检查的命令批次墙钟时间约为 `0.007` 秒；完整实验没有单独计时，不能把这个数字当作端到端诊断耗时。
- 与 README 描述是否一致：在本次受控实验中一致；Skill 的确促使 Agent 先建立反馈信号，再复现、提出假设并定向检查。
- 修复状态：没有修复。用户本次要求是“诊断”，所以只确认根因，不把程序变绿。

## 遇到的问题与排查过程

### 问题一：`50.00` 没有获得免运费

- 现象：规则要求小计达到 `50.00` 时免运费，CLI 实际返回 `5.00`。
- 最初判断：可能是比较符号错误、阈值常量错误或输入金额在解析时发生偏移。
- 实际原因：`Decimal(raw_subtotal) - Decimal("0.01")` 让 `50.00` 在比较前变成 `49.99`，等效免运费边界被推迟到 `50.01`。
- 解决方法：本次没有实施修复；若进入修复阶段，应先把最小复现固化为回归测试，再移除错误的 `0.01` 偏移。
- 如何确认已修复：待修复后重新运行原始 `check_bug.py`，要求同一条命令从红色变为绿色；目前不能宣称已修复。

### 问题二：如何避免实验者提前知道答案

- 现象：如果 Agent 自己写下唯一故障，就可能在诊断前已经知道根因，实验无法证明反馈流程的价值。
- 实际处理：预先准备三种产生相同表面症状的实现，通过随机选择决定实际故障；在失败命令稳定变红前不查看选择结果。
- 判断：这个设计降低了“直接记住自己刚写的 Bug”的干扰，但仍然只是受控实验，不等同于完全盲测。

## 我真正学到了什么

### 技术层面

- 有错误信息还不够；反馈信号必须精确对应用户症状，能够稳定复现，并能在修复后使用同一标准转绿。
- 可证伪假设比单一猜测更可靠。每个假设都要给出一个能让它成立或被排除的预测。
- 黑盒结果和源码证据应该互相印证。只看到可疑代码，不代表它就是实际触发症状的原因。

### 产品层面

- 它为谁创造了什么价值：帮助开发者和团队约束 AI 编码过程，减少无证据试错和“改了但没有证明修好”的情况。
- 真正影响体验的关键指标：复现成功率、反馈循环耗时、失败信号是否对应真实症状、修复后的回归覆盖，以及 Agent 是否遵守阶段门控。
- 哪些异常状态需要向用户解释：无法复现、反馈信号不稳定、缺少环境访问、只能看到脱敏后材料、没有合适测试边界，以及诊断完成但尚未修复。
- 如果由我设计，会增加或优化什么：为每次诊断生成简短的证据记录，明确列出原始症状、反馈命令、被排除的假设、最终根因和修复状态。

### 对金融 AI、漫剧或视频产品的启发

- 可以迁移的能力：把模型输出错误、数据处理异常或生成流程故障转换成可重复输入和明确通过/失败标准。
- 可能的应用场景：金融规则计算边界错误、RAG 检索错配、Agent 工具调用失败、视频生成工作流中某一阶段的输入输出异常。
- 不能直接迁移的原因：很多 AI 输出是概率性的，无法直接使用普通单元测试；需要固定模型版本、随机种子、数据集或采用统计评估，才能建立足够稳定的反馈信号。

## 局限与风险

- 技术限制：Skill 是流程约束，不会自动保证反馈循环正确，也不会替代领域知识。
- 使用门槛：需要能够构造可复现输入、识别正确测试边界，并理解什么结果才代表用户的真实症状。
- 性能或成本：受控实验非常快，但真实系统的端到端测试、浏览器回放或线上观测可能耗时且有基础设施成本。
- 数据与隐私：诊断日志、网络请求和追踪文件可能包含凭据或用户数据，必须先脱敏；本次实验未使用真实数据。
- 商业化限制：代码采用 MIT License，但团队使用时仍需自行评估第三方依赖、内部代码和数据的合规要求。
- 目前尚未验证的部分：真实大型项目、非确定性 AI 故障、多人协作、不同模型以及多个 Skills 组合时的效果。

## 我的最终判断

> 我的结论：`mattpocock/skills` 解决的是 AI 编码过程缺少工程约束的问题，而 `diagnosing-bugs` 的核心不是直接给出答案，是先把 Bug 变成可重复、可证伪的反馈循环。本次受控实验确认了这一流程能够阻止 Agent 在没有红色信号时直接猜原因，并通过逐个排除假设找到输入金额被错误减去 `0.01` 的根因。它值得继续试用，但一次微型实验只能证明流程可执行，不能证明它在所有真实工程中都有效。
