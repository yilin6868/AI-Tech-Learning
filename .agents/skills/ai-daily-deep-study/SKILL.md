# 每日 AI 技术深度学习 2.0

把日报当作学习过程的证据，而不是完成任务的终点。每天可以浏览多个候选，但只深入研究 **一个项目和一个主要技术问题**。默认采用对话式引导：每一阶段说明为什么做、给出一个可执行的小任务，等用户反馈后再进入下一阶段。用户明确委托全程执行时，可以代为阅读、试用和起草，但仍要展示关键判断和未验证之处。

## 先确认起点

1. 在仓库根目录工作；先阅读 `README.md`、`daily/README.md`、`templates/daily-note-template.md`，检查当天 `daily/YYYY/MM/YYYY-MM-DD.md` 是否已存在。使用用户所在地日期；不确定时询问，不擅自覆盖已有日报。
2. 确认用户现在处于哪一步：没有候选、已有候选链接、已选定项目、已读文档、正在试用，或只差复盘。只补齐缺失步骤，不要求重做已经完成的研究。
3. 如果用户还没选项目，询问当天最想弄懂的技术问题或应用方向；如果已给候选，直接从候选评估开始。

## 研究路径

### 1. 发现与筛选

- 对“今天最新”“本周更新”的信息，实时核对 GitHub Trending、候选仓库的 Release/提交记录和官方文档，写明查看日期与链接。不要把 Trending 排名、Star 数或宣传语当作技术质量或发布时间的证明。
- 给每个候选记一行：它解决什么问题、最近有什么可核实的变化、能否在当前环境做一个小实验、与用户的 Agent/RAG、金融 AI、漫剧或视频兴趣有什么关联。
- 若有多个候选，推荐 **一个**，用“学习价值 × 可验证性 × 当前相关性”解释取舍；保留其他候选的简短未入选理由。不为凑日报同时深挖三个项目。
- 将项目收窄为一个能检验的问题，例如“它是否真的能跨会话找回最新状态？”，而不是“研究整个项目”。

### 2. 阅读并用自己的话复述

- 从 README 的定位、最小使用示例开始，再按当前问题选择官方架构、配置、API、源码入口或相关 Issue/Release；不要机械要求每个项目阅读相同的五篇文档。用户找不到页面时给直接链接、仓库内路径和阅读顺序。
- 让用户用“输入 → 核心处理 → 输出”复述工作链路；对每个关键组件说清作用、输入、输出。区分**官方原文主张**、**自己的理解**和**源码/实验已证实的事实**。
- 一次只解释当前障碍所需的概念。优先用短例子和具体操作，不把完整架构一次性倾倒给初学者。无法确认的细节标为待查证。

### 3. 用大白话再讲一遍

- 专业解释完成后，再增加一层独立的大白话解释；它用于帮助理解，不能替换专业术语、证据、命令、数据和适用边界。
- 优先回答五个问题：它是什么、解决什么问题、怎么工作、可以类比成什么日常事物、目前还不能证明什么。比喻必须与真实机制对应，不能为了好懂而改变事实。
- 用一个具体例子把抽象流程串起来，句子要短，避免在同一段继续引入新的术语。可以采用“普通做法容易怎样 → 这个技术要求怎样 → 最终带来什么变化”的结构。
- 请用户用两三句话复述“它解决什么问题、核心办法是什么、刚才确认了什么”。如果仍然说不清，就继续简化或回到对应专业概念，不急着进入实验。
- 写日报时保留原有专业分析，并在靠前位置增加独立的“## 大白话解释”小节。该小节只复述已经核实的事实，不覆盖、不删改后面的专业内容。

### 4. 设计最小可验证实验

- 在安装前写下假设、成功标准、失败标准、最小操作路径，以及如何排除“模型猜对了”或“只复述当前对话”的替代解释。优先选择无需付费、可回退、可在本机完成的实验。
- 记录版本、日期、操作系统、使用端、重要配置和外部依赖；公开日报中不得写入密钥、个人数据或未经同意的私有内容。对安装脚本、Hook、后台服务、遥测、费用与数据上传先说明影响，再让用户做知情选择。
- 若用户亲自操作，先给一个具体动作和预期现象，再请用户贴出结果；如遇失败，先定位失败发生在安装、启动、数据写入、检索还是答案生成，不要直接把“安装成功”当“功能验证成功”。

### 5. 核对证据与形成判断

- 记录实际命令或操作、观察到的输出、错误、耗时和可复查证据。检索命中、最终回答正确、底层检索耗时、端到端等待时间是不同结论，不要混写。
- 若证据有新旧冲突，按时间核查最新记录，并说明旧结论为何被取代；不要仅因找到相关旧材料就宣称当前状态。
- 若实验失败或受环境限制，照实写“未验证”、失败原因和下一步，不编造成功或性能数据。总结技术原理、适用边界、产品启发及值得继续追踪的 Release/Issue。

### 6. 写日报并回看

- 使用 `templates/daily-note-template.md` 的结构，把对话过程中已经核实的内容写入 `daily/YYYY/MM/YYYY-MM-DD.md`；有现成日报就继续完善。模板是提问清单，不必为填满每个小节而补造材料。
- 资料来源给可打开的原始链接，注明核查日期；结论清楚标出“官方说明 / 个人理解 / 实验事实 / 待验证”。日报应让读者复现实验，也让未来的自己看懂为什么改变判断。
- 写完先请用户用两三句话回答：“这个技术解决什么问题？核心机制是什么？你亲自验证了什么？”如果答不上来，回到对应阶段补学，而不是急着发布。
- 最后只给一个具体的下一步实验。周报用于跨天归纳，不自动把当天研究包装成趋势。提交或推送 GitHub 前检查隐私与差异，并遵循用户本次授权；不要自动发布未审阅的草稿。

## 每轮引导的输出形态

保持简洁，优先用下面四项，让用户能立即行动：

1. **当前阶段**：已经确认了什么，还有什么未确认。
2. **为什么这一步重要**：一句话说明它能排除什么误判。
3. **现在只做这一件事**：给出具体链接、阅读段落、操作或问题。
4. **完成后告诉我什么**：指定需要回传的现象、截图、命令结果或自己的复述。

不要在用户尚未完成前面的动手步骤时，假装已完成整篇日报。用户只要求讲解时，不擅自安装软件、修改配置或发布内容。
